# 1. ebpf 数据采集

基本思路：程序在 OceanBase`observer`进程的`ObMySQLRequestManager::record_request`函数入口挂 uprobe，每条 SQL 审计记录命中一次；在内核态把审计数据提取出来，经 ringbuffer 交给用户态 agent，再经 gRPC 送到 collector 落 MongoDB。

```
observer.record_request ──(uprobe)──▶ BPF handle_uprobe ──▶ rb RINGBUF(64MB)
                                                                │
                                                    agent(uprobe.cpp) 自轮询消费
                                                                │ gRPC AuditBatch
                                                                ▼
                                                    collector ──▶ MongoDB(ob_audit.audit_events)
```

## 1.1. 实现细节

### 1.1.1. 数据分片：

OceanBase 单条 SQL / 绑定参数（params）可以很大，而 ringbuffer 里 main event 用的是定长 bucket，不可能给每条事件都留 64KB。因此设计上：

- main event 内只放 SQL / params 的**首片**（`AUDIT_MAIN_SQL_PAYLOAD_MAX=1023`，`AUDIT_MAIN_PARAMS_PAYLOAD_MAX=255`，`src/audit_record.h:20,24`）；
- 超出部分拆成独立的**fragment 记录**（`struct audit_fragment_record`，`src/audit_record.h:44`），用`parent_event_seq`/`next_fragment_seq`串成链，agent 侧按链重组还原完整 SQL。

**基线的分片粒度**：单片上限`AUDIT_FRAGMENT_PAYLOAD_MAX=4095`、每字段最多`AUDIT_MAX_FRAGMENTS_PER_FIELD=16`片。即一个 64KB 的 SQL 要被切成最多 16 片、在 BPF 内**循环**逐片`reserve → read → submit`。

### 1.1.2. 数据拷贝进ringbuffer

在原来的设计中，BPF 内核态**既抓取也解析**：

1. `reserve_audit_record(main_out_size)`按实际大小从 ringbuffer 预留一块 bucket；
2. 对约**35 个标量字段**（status / trace\_id / 各类 id / 时间戳 / sql\_id / stmt\_type / trans\_status / addr…）逐一`bpf_probe_read_user`从 observer 用户内存读出，直接解析回填进`struct event`头；

```c
// a4646dd  src/uprobe.bpf.c（现已删除，节选）
read_i32(audit_record, OB_AUDIT_STATUS_OFF, &e->ret_code);
read_u64(audit_record, OB_AUDIT_REQUEST_ID_OFF, &e->request_id);
read_u64(audit_record, OB_AUDIT_TENANT_ID_OFF,  &e->tenant_id);
// ...累计约 35 次分散读

```

3. 再对 6 个变长字段读 ptr\+len，把内容拷进`payload`。

### 1.1.3. 提交数据，唤醒外部消费

一块 event（及每个 fragment）填好后`bpf_ringbuf_submit(e, 0)`提交：

```c
// a4646dd  src/uprobe.bpf.c（现已删除）
bpf_ringbuf_submit(e, 0);   // flag=0：默认行为，提交即触发 irq_work 唤醒消费者
bpf_ringbuf_submit(s, 0);   // fragment 同样 flag=0

```

flag=0 表示每次提交都会触发内核`irq_work`唤醒用户态消费者；agent 侧相应地用`ring_buffer__poll(rb, 100)`（`src/uprobe.cpp`，基线）靠 epoll 被唤醒后消费。

## 1.2. 优化思路和结果

优化针对上面三个阶段各暴露的一个问题；每个问题按**问题 → 为什么这么优化 → 结果**展开。

### 1.2.1. 问题一：逐字段读取的开销。

**问题**：约 35 次分散`bpf_probe_read_user`全部发生在 SQL 执行热路径上，直接抬高 observer 内核态 CPU；且分散读的目标偏移各不相同、又叠加变长 payload 链式累加，BPF verifier 难以剪枝。

**优化**：`struct event`新增一块`ob_raw[1728]`，把审计记录的**连续定长区一次性 bulk 读走**，标量一律不在内核解析，下沉到 collector：

```c
// src/uprobe.bpf.c:203
e = reserve_audit_record(AUDIT_RINGBUF_BUCKET_MAIN);
// src/uprobe.bpf.c:209 —— 一次读入 1728B，替代 ~35 次分散读
if (bpf_probe_read_user(e->ob_raw, OB_AUDIT_RAW_FIXED_SIZE, audit_record)) { ... }

```

标量解析移到用户态`event_fill_scalars_from_ob_raw()`（`src/uprobe.h:303`，collector 侧`mongo_insert_worker.cpp:20`调用），按`OB_*_OFF`从`ob_raw`里`memcpy`抽取。内核态用户读取从**35 → 8**次（1×is\_inner 过滤 \+ 1×bulk \+ 6×变长字段）。

**为什么这么做**：定长区在内存里本就连续，一次读走比拆 35 次省下大量 probe 开销；而“怎么解释这些字节”既不需要内核特权、也不紧急，挪到**无 verifier 约束、可水平扩展**的 collector 更划算——把成本从稀缺的 DB 内核热路径转移到便宜的采集侧。

**结果**：内核读取 35→8；压测（rw-512 干净 3v3 A/B）QPS 影响从旧版**−6.23%**收窄到**−5.07%**，**p99 延迟回退减半**。代价：agent 转发未裁剪的整块 1728B`ob_raw`→**net\_tx \+66%、RSS \+34MB**（待后续按实际用到的偏移裁剪）。

### 1.2.2. 问题二：分片太细

**问题**：基线单片 4095B、每字段最多 16 片，捕获一个 64KB SQL 要在 BPF 内**循环切 16 片**。目标内核 5.8 无 bounded-loop，循环只能全展开 →**verifier 状态爆炸**；且多片意味着多次`reserve/submit`和用户态多次重组，分片开销大。

**优化**：单片上限提到 64KB、每字段最多 1 片：

```c
// src/audit_record.h:61,66
#define AUDIT_FRAGMENT_PAYLOAD_MAX 65535   // 4095 → 65535
#define AUDIT_MAX_FRAGMENTS_PER_FIELD 1    // 16 → 1

```

`emit_field_fragment`因此变成**单次**`reserve → 一次 read → submit`，彻底无循环：

```c
// src/uprobe.bpf.c:130-147（节选）
s = bpf_ringbuf_reserve(&rb, AUDIT_FRAGMENT_BUCKET, 0);   // 一片 ~64KB
copied = fragment_payload_size(remaining);
AUDIT_FORCE_AND(copied, 65535);
bpf_probe_read_user(s->payload, copied, src + first_offset);  // 一次拷贝替代 16 片循环
bpf_ringbuf_submit(s, BPF_RB_NO_WAKEUP);

```

**为什么这么做**：OB sql audit本身也会按照64KB的sql长度截断，和其对齐，不需要 16 片。代价是分片事件`reserve`时会瞬时占用整个 ~64KB bucket（相对真实长度有内存浪费）——**但实测agent 消费很快、ringbuffer 几乎不积压**，这点瞬时内存浪费完全可以接受。本质是**用空间换取“消除循环 → 消除 verifier 爆炸 \+ 砍掉多片分片/重组开销”**。

**结果**：verifier 状态爆炸消除，字段/大对象扩展不再受内核循环限制；分片路径的`reserve/submit`/重组次数骤降；≤64KB 的大 SQL 仍能单片完整捕获。

### 1.2.3. 问题三：提交导致消费唤醒太多

**问题**：原来`submit(_, 0)`每次提交都触发`irq_work`唤醒消费者。SQL 审计频率极高，海量唤醒/调度开销累积在**生产侧（observer 线程）**，进一步抬高 DB CPU。

**优化**：两处 submit 改为`BPF_RB_NO_WAKEUP`，生产侧不再唤醒；agent 改为**自轮询**消费：

```c
// src/uprobe.bpf.c:147 / :362
bpf_ringbuf_submit(e, BPF_RB_NO_WAKEUP);   // main 与 fragment 两处 flag 必须一致
// src/uprobe.cpp:549
int consumed = ring_buffer__consume(rb);   // 由 poll(epoll 唤醒) 改为主动 consume + 空闲退避

```

**为什么这么做**：既然 agent 消费很快、几乎实时清空 ringbuffer，就**不需要内核发唤醒来“通知有数据”**。去掉唤醒把这部分开销从 DB 热路径（observer 线程）彻底移除——用 agent 侧一点点空转/退避 CPU，换 observer 侧 CPU。

**结果**：observer 侧的提交唤醒开销消除；agent 自轮询 \+ 空闲退避（1ms→5ms）在无积压时维持低延迟消费。

# 2. agent 高性能数据上送

数据流概览：

```
 observer 线程 (OB DB 热路径)
    │  bpf_ringbuf_submit(NO_WAKEUP)              §3.3：生产侧不唤醒
    ▼
 ┌──────────────────────────────┐
 │  缓冲区①  内核 BPF ringbuffer  │  64MB，生产者=observer
 └──────────────────────────────┘
    │  ring_buffer__consume() 自轮询 + 空闲退避    §5.6 优化点：轮询拉取
    ▼
 handle_event ── 分片记录? ──► pending 环 (VarlenRingBuffer) 按 event_seq 重组超长 SQL/params
    │ 未分片 / 重组完成                                │
    ▼◄────────────────────────────────────────────────┘
 ┌──────────────────────────────┐
 │  缓冲区②  用户态 batch 内存池  │  64MB，预分配 Batch[] 复用，稳态零 malloc
 │  current_batch ─ append 组批 ─ 封批 ─► ready_batches 队列
 └──────────────────────────────┘
    │
    ▼
 N × sender_worker (并发，各持独立 stub)
    │  round_robin 多地址 channel（keepalive + 健康退避）
    ▼
 collector-1 / collector-2 / …    ← etcd 服务发现 (Range + Watch)，地址集变更热切 channel
```

## 2.1. 实现细节

首先在收到通知后，唤醒程序从ringbuffer中消费数据，然后写入发送缓冲区，在由多worker基于grpc实现上送。

### 2.1.1. 缓冲区

从内核 ringbuffer 拉出记录后，agent 在用户态管两个缓冲区：组合缓冲区和发送缓冲，把“分片重组”和“批量上送”两件事分开。

- 缓冲区①：组合缓冲区`pending`（`VarlenRingBuffer`，默认 16MB）。专门重组被 §3 分片的超长 SQL/params：主记录先按`event_seq`在这里占一整段，后续 fragment 逐片填入，收到尾片后拼成一条完整逻辑记录。未分片的事件不进组合缓冲区。
- 缓冲区②：发送缓冲（发送队列内存管理，`BatchPool`，默认 64MB）。一组预分配、可复用的 batch 内存块（`pool_bytes / batch_bytes`=64MB / 256KB），运行期只从空闲索引栈借还、反复复用，热路径零内存申请。完整记录——无论是组合缓冲区拼好的，还是未分片直接来的——都插入这里的当前 batch，攒成批量。

![图片](https://office.netease.com/api/pub/file/download?path=popo%2F2026%2F08%2F21%2Fa724c83ba204481c9057444a19428b27.png&code=YnJ2OGlhZzBfMTc4NzU1NTI5MDgyNg%3D%3D)

组合缓冲区把碎片拼成整条，发送缓冲把整条攒成批量——记录进入发送缓冲后，就进入下一步的组批与封批。

### 2.1.2. 组批与封批

进入发送缓冲的每条完整记录，先被就地`append`进当前 batch 的 payload（追加后原地回填`server_ip`，省掉一次中间拷贝），多条攒成一个大批次一起上送。

当前 batch 在三种情况下“封批”——从`current_batch`推入待发送的`ready_batches`队列：

1. 写满：append 后累计字节达到`batch_bytes`（或再加一条会溢出，则先把上一批封掉）。
2. flush 到期：距该批第一条记录已过`flush_interval_ms`，由 sender 用条件变量的定时等待精确触发。小流量时，保证数据也会正常上送，不会阻塞在内存。
3. 停止：`stop()`/`flush()`收尾时封掉残批。

为避免每条记录都唤醒 worker 造成的调度/futex churn，只有封批时才唤醒；未封批时仅在“新 batch 的第一条记录”唤醒一次 worker 去设定 flush 截止时间：

```c
// src/audit_grpc_sender.cpp  grpc_submit_locked
if (!sealed && first_record)
    impl->cond.notify_one();

```

封好的批次进入`ready_batches`队列，等待 worker 取走——这就是下一步的并发上送。

### 2.1.3. 并发上送

`upload_concurrency`个`sender_worker`线程（默认 2、上限 8）并发工作：各自从`ready_batches`队列 pop 一个批次，经 gRPC 上送，送完把 batch 归还内存池。每个 worker 持有自己的 gRPC stub，只有在 channel 发生热切（版本号变化）时才重建 stub，避免并发争用和频繁建栈。

worker 具体把批次发往哪个 collector、某个 collector 挂了怎么办，由下面的负载均衡与容灾决定。

### 2.1.4. 负载均衡和容灾

- 负载均衡：所有 worker 共用一个多地址 channel，用 gRPC 原生`round_robin`策略把批次在 subchannel 级均匀打到多个 collector；早期的`hash_agent`选路已废弃。
- 服务发现与热切（容灾核心）：resolver 分静态单地址与 etcd 两种；etcd 用`Range`拉全量 \+`Watch`收增量，collector 上下线导致地址集变化时，发现线程在锁外重建 round\_robin channel，再在`switching`屏障下原子热切（换 channel、版本号 \+1），worker 每次上送重读目标、版本变了就换 stub。
- 连接健康：round\_robin channel 自带 subchannel 健康检查与退避重连，叠加 keepalive ping（15s / 5s），不必等 etcd 租约超时就能剔除坏连接。
- 退避重试：单批上送失败按指数退避重试（默认共 4 次，100ms→翻倍→上限 500ms）；重试耗尽才丢弃该批并计入 agent 侧丢失指标。
- 容灾持久化：本地只落`event_seq`单调 checkpoint（对应`4d667aa`）——重启时读回并预留一段，保证序列号跨重启仍单调、下游对账不重号；审计负载本身不落本地盘，上送失败重试耗尽即丢。

## 2.2. 从ringbuffer中消费数据的优化

之前的实现（`a4646dd`）：主循环用`ring_buffer__poll(rb, 100)`消费——基于 epoll，阻塞至多 100ms 等待内核唤醒后取数。

```c
// a4646dd  src/uprobe.cpp（现已删除）
while (!exiting) {
    err = ring_buffer__poll(rb, 100);   // 依赖 BPF submit 触发的 irq_work 唤醒
    ...
}

```

问题：`ring_buffer__poll`依赖内核 epoll唤醒来“通知有数据”。但 §3.3 已把 BPF 侧 submit 改为`BPF_RB_NO_WAKEUP`——生产侧不再唤醒消费者。两者语义不再匹配：消费端继续等唤醒就收不到及时通知，只能退化为纯超时轮询。消费侧必须改为主动拉取。

优化：主循环改用`ring_buffer__consume`主动抽取 \+空闲退避（`src/uprobe.cpp:706-728`）：

```c
const unsigned int idle_min_us = 1000;   // 忙转空后起始睡眠 1ms
const unsigned int idle_max_us = 5000;   // 上限 5ms，对齐 gRPC flush_interval
const unsigned int idle_step_us = 500;   // 每次空轮询线性 +500us
unsigned int idle_sleep_us = 0;
while (!exiting) {
    int consumed = ring_buffer__consume(rb);   // 主动抽干当前所有就绪记录
    ...
    if (consumed > 0) { idle_sleep_us = 0; continue; }   // 忙：清零，连续抽干
    idle_sleep_us = idle_sleep_us < idle_min_us ? idle_min_us
                    : min(idle_sleep_us + idle_step_us, idle_max_us);  // 闲：线性退避
    std::this_thread::sleep_for(std::chrono::microseconds(idle_sleep_us));
}

```

为什么这么做：

- `NO_WAKEUP`之后没有唤醒信号，消费必须主动轮询；`consume`一次把当前就绪记录全部抽干。
- 忙时清零 sleep：紧贴生产速率连续抽干，ringbuffer 几乎不积压——这正是 1.2.2 “分片瞬时占 64KB、内存浪费可接受”和 1.2.3 “去唤醒”成立的前提。
- 闲时线性退避：避免空转烧 CPU；稳态“抽干→睡”循环约 1000 次/s（idle\_min=1ms）。
- `idle_max=5ms`对齐 gRPC`flush_interval`（部署配置 5ms）：ringbuffer 层最多引入 5ms 拉取延迟，而这段延迟本就被 sender 的 flush 周期掩盖，不额外增加端到端上送时延。

结果：

- 与 1.2.3 小节的`NO_WAKEUP`配成一对：把唤醒/调度开销从observer（DB 热路径）整体移除，代价是 agent 自身一点可控的低空转 CPU（闲时退避后最多 ~200 次/s 轮询）。
- 稳态下 ringbuffer 近乎清空、低延迟上送；高峰忙时连续抽干，不因“没有唤醒”而漏收数据。

# 3. collector快速入库.

collector 收到 agent 上送的批量后，把记录落进 MongoDB。

```
 agent 批量 ── gRPC Upload ──► 解析 + 打包 MongoInsertTask
  (多个并发 RPC = 多生产者)          │ try_push（非阻塞；满则 QUEUE_FULL 背压回 agent）
                                     ▼
                        ┌───────────────────────────┐
                        │  有界队列 BoundedMpmcQueue  │  容量默认 1024
                        └───────────────────────────┘
                                     │ pop（阻塞）
             ┌───────────────┬───────┴───────┬───────────────┐
             ▼               ▼               ▼               ▼
          worker1         worker2         worker3         worker4   (多消费者，默认 4)
             └────────────── 共享 client pool (1~4) ──────────────┘
                                     │ bulk 无序 insert_many（≤1000 条 / ≤4MB 一批）
                                     ▼
              MongoDB（唯一索引去重 + ingest_time TTL + audit_schemas 版本字典）
```

## 3.1. 多生产者多消费者模型

collector 把“收 RPC”和“写库”彻底解耦——网络快、Mongo 慢时用一个有界队列吸收，多个 worker 并发写库来抵消单次写延迟。

- 生产者：gRPC`Upload`处理线程（多个 RPC 并发）。每个 Upload 把整批记录解析、打包成一个`MongoInsertTask`，`try_push`进队列（`audit_collector.cpp`→`mongo_workers_->submit`）。
- 有界队列：`BoundedMpmcQueue`（`mutex`\+`not_empty/not_full`两个条件变量 \+`deque`），容量`queue_capacity`（默认 1024）。`try_push`非阻塞：队满立即返回`false`。
- 消费者：`MongoInsertWorkerPool`的 N 个 worker（默认`insert_concurrency=4`）。worker 阻塞`pop`取任务，调`MongoSink::insert_events`写库，失败退避重试（0 / 100 / 200ms，最多 4 次），完成后触发回调更新丢失/入库指标；`stop()`时`close()`队列并 join。
- 背压闭环：队满 →`Upload`回`UPLOAD_STATUS_QUEUE_FULL`→ agent 收到后重试该批。重试安全性由入库侧的唯一键幂等保证。

worker 从队列取到任务后，接下来就是怎么写进 Mongo。

## 3.2.  MongoDB 入库设计

- 共享连接池：进程级`client pool`（`pool_min/max_size`=1 / 4），worker 用时`pop`、用完`push`回，避免每批重新建连。
- 批量分块写：一个 task 内先 build 全部 BSON doc，再按`bulk_max_records`（1000）/`bulk_max_bytes`（4MB）切成 chunk，逐 chunk 调`insert_many`。
- 无序插入（`ordered=false`）：同一 chunk 里一条坏 doc 不阻塞其它；对重复键错误单独放行（视作成功），配合唯一索引实现幂等。
- 写关注`w1`\+`wtimeout`2000ms：主节点确认即返回；副本集迟迟不确认时按超时失败，避免 worker 无限阻塞。失败（非重复键）→`insert_events`返回 false → worker 重试，耗尽计入`db_retry_exhausted`。
- 索引 / TTL / schema：
    - 唯一复合索引`{tenant_id, server_ip, event_seq}`——去重幂等的依据：agent 重试或乱序 resend 命中重复键即跳过，不会重复入库。
    - TTL 索引：`ingest_time`字段按`event_ttl_days`（3 天）自动过期删除。
    - 辅助索引`idx_tenant_time`/`idx_server_time`：以`ingest_time`结尾，支撑按租户/实例的时间范围查询。
    - schema 版本字典：schema 以`{_id: version}`upsert 进`audit_schemas`集合，每条 doc 带`sv`版本，供下游按版本解码。

上面说的“build BSON doc”，doc 里的字段是怎么从一条`event`映射出来的——就是字段映射。

## 3.3. 字段映射

- 标量下沉解析（对应1.1.2）：BPF 侧不解析标量，collector 用`event_fill_scalars_from_ob_raw`从`ob_raw`按`OB_*_OFF`常量偏移抽出命名字段：`ret_code`、`trace_id`、`request_id`、`session_id`、`tenant_id`/`user_id`/`db_id`、`affected_rows`/`return_rows`、`stmt_type`/`trans_status`、`sql_id`、`client_ip`，以及请求时间戳/耗时等派生量。
- 变长与地址字段：`user_name`/`proxy_user_name`/`tenant_name`/`db_name`按各自`*_len`截断 UTF8；`query_sql`/`params_value`按 payload 长度取；`client_ip`/`server_ip`走地址格式化、`trace_id`/`sql_id`走各自格式化。其中`server_ip`参与唯一索引，取事件内地址、为空回退到请求的`server_ip`。
- 数值键压缩：`audit_schema.json`（`{version, fields:{"0":"total_size", … ,"46":"record_offset"}}`，47 个全名映射到`0..46`）驱动一张“全名→数值键”表；写 doc 时用数值键（如`"3"`）而非全名（如`"event_seq"`），大幅缩小文档体积；每条 doc 带`sv`版本，下游据此还原全名。仅保留一个真名`ingest_time`（DATE\_TIME）供 TTL 使用。
